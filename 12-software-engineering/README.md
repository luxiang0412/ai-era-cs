## 为什么要学

模式和原则容易学成名词收藏。有用的部分是边界：哪一段会变，哪一段必须稳。一个接口从「能跑」到「能上线、能被别人接手」，差的就是这一层。AI 写代码以后，这一层更重要：写得快了，判断哪段该留、哪段该删的人还是你。

## 建议顺序

1. **开发流程** — 生命周期、需求分析、团队协作。先知道一个需求从提出到上线要经过哪些人和哪些检查。
2. **设计原则** — 模块化、高内聚低耦合、SOLID。拿一个自己写过的模块对照，看依赖是不是朝一个方向。
3. **设计模式** — 少记几个真的会用的：策略（把变化的算法换掉）、观察者（事件）、适配器（把一个接口凑合成另一个）。见到的时候能认，不要按目录背 23 个。
4. **重构与技术债** — 小步改、每步都能跑测试。技术债要记下来，写清楚利息是什么。
5. **代码审查与规范** — 审查是找「以后会疼」的地方，不是挑空格。
6. **API 与 SDK 设计** — 名字、错误、版本、向后兼容。接口一旦发出去就很难收回。
7. **依赖与文档** — 依赖的版本和来源；文档写给三个月后的自己。
8. **AI 辅助开发** — Coding Agent 工作流：写 spec、让它改、自己审、跑测试。和 [26](../26-llm-agent-systems/README.md) 里的 Harness 对着看。

## 书和课

- 《A Philosophy of Software Design》（John Ousterhout），关于深度和复杂度的几章
- 《重构》（Martin Fowler）
- 《设计模式》当字典
- [Software Engineering at Google](https://abseil.io/resources/swe-book)，讲规模和时间对代码的影响

这一节的「demo」可以是给前面某一个协议或数据结构补测试和日志，再做一次重构：失败时打印在途的序号，而不是只抛一个 `Error`。
