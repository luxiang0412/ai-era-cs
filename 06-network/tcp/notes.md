# TCP 笔记

## 踩坑

- 握手不是登录，也不是加密。它只把两边的起始序号和一些能力对上。加密、证书是 TLS 的事，发生在 TCP 已经建立之后。用 Wireshark 看 HTTPS 时，前三个带 SYN 的包还是明文的 TCP 头。
- 「粘包」不是 TCP 坏了。TCP 交给应用的是字节流，没有消息边界。两次 `write` 可能被一次 `read` 读完，也可能被拆开。要边界，就在应用层自己加长度或者分隔符。
- TIME_WAIT 挂在主动关闭的一方。如果服务端先关连接，占着的是服务端端口。马上重启，有时会 `Address already in use`。
- 接收窗口变成 0，通常是对端的应用没把缓冲区读走，不是路由坏了。Node 里只写不消费对端的数据，连接也会慢慢停住。
- 超时设得比往返时间还短，会制造一堆「没丢也重传」。demo 里把 `--rto` 改成 `30` 就能看见。

## 好问题

- 确认号为什么是「对方序号 + 1」，而不是对方序号本身？SYN 和 FIN 占不占号？
- 第三次握手的 ACK 丢了。客户端觉得连上了，服务器还停在 SYN_RCVD。客户端接着发的业务数据会怎样？
- 接收窗口很大，下载还是慢。这时候该怀疑谁，接收方还是路径？
- HTTP/2 把很多请求复用到一条 TCP 上。其中一个包丢了，为什么别的请求也得等？QUIC 想躲开的是哪一件事？

## 原来如此

- 累积确认是一个数字认一整段。洞后面的字节可以已经躺在接收方的缓存里，确认号却一步都不动。应用仍然读不到洞后面的内容。
- 流量控制看的是对方的缓冲，拥塞控制看的是路堵不堵。真正能飞在路上的量，是这两个窗口里更小的那个。
- 这个目录里的 demo 一个字一个序号，只是为了把窗口看清楚。回到真 TCP，序号是字节偏移。看完动画要记得把这个简化还回去。
