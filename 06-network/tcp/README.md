# TCP：把不可靠的投递变成一条按序的字节流

[← 网络](../README.md)

IP 负责把一个个数据报往目的地送。送到没有、送了几次、谁先谁后，它不管。网页、接口、SSH 却希望：我写出去的字节，对面按同样的顺序读到。TCP 干的就是这件事。

动画：[三次握手与四次挥手](viz/handshake.html)，[滑动窗口](viz/sliding-window.html)。能跑的协议在 [`demo/`](demo/README.md)。容易混的点在 [`notes.md`](notes.md)。

## 一句话版

TCP 维持一条按顺序、不丢、不重的字节流。办法就几样：给字节编号，对方确认收到了哪里，没确认的过一会儿再发，同时限制「已经发出还没确认」的数量，免得把对方或网络灌满。

## 生活类比版

两个人用对讲机传一份逐页编号的稿子。线路很吵，页会丢、会重复、会后发先至。

- 开工前先对表。我从第 100 页起，你从第 300 页起。两边都听清了对方的起始页，才开始传。只喊一来一回不够，因为喊的人不知道对方听见没有。
- 你收到 100、101、102，回一句「下一页我要 103」。这一句把 103 之前的全认了，所以叫累积确认。
- 你桌上只能摊开 4 页。我就最多先发 4 页，不必每页都干等。你处理得慢，就少报一点能摊开的数量。这是流量控制，保护的是你的桌子。
- 某一页没有回音，超时之后把这一页再发一次，不必从第一页重来。
- 稿子是双向的。我说「我讲完了」和你说「我也讲完了」是两件事，各要一次确认，所以关掉常常是四个来回。
- 桌子很大，楼道仍可能堵。发送方还得自己节流。这是拥塞控制，保护的是路，不是对方的桌子。

类比到这里为止。下面的细节里，页码其实是字节编号，不是数据包编号。

## 深入细节版

### 为什么需要 TCP

IP 是尽力而为。路由器队列满了就丢，同一条连接上的包也可能走不同路径，于是乱序。UDP 几乎就是 IP 加上端口：一个数据报一份消息，丢了就丢了。直播、DNS 这类「晚了不如不要」或者「我自己会重试」的场景用得上。

文件和接口不能少一个字节。每个应用自己做重传当然可以，早期也有人这么干。TCP 把可靠、按序、流量控制做成公共部分，应用只看到能读能写的流。

代价也明确：要记状态，至少多一次往返，队头有洞时后面到了的数据也先不能交给应用。HTTP/3 改走 QUIC，很大一块原因就是不想被 TCP 这一条流里的一个丢包挡住所有请求。

### 三次握手

连接刚开始，两边各有一个初始序号（ISN）。序号不好从 0 公开用起：上一轮连接迟来的包会和新建的撞上。真连接里的 ISN 是随机挑的。图里用 100 和 300，只是为了能心算。

客户端序号记作 `x`，服务器记作 `y`。

1. 客户端 → 服务器：`SYN, seq = x`。客户端进入 SYN_SENT。SYN 占一个序号。
2. 服务器 → 客户端：`SYN + ACK, seq = y, ack = x + 1`。服务器进入 SYN_RCVD。`ack = x + 1` 表示：x 以及它之前的我都认了，下一字节我等 x + 1。
3. 客户端 → 服务器：`ACK, ack = y + 1`。两边进入 ESTABLISHED。

为什么不是两次？两次结束时，只有客户端知道「对方收到了我的起始序号」。服务器发出去的起始序号有没有送到，它自己不知道。第三次就是回「你的序号我听到了」。

握手时还会交换窗口大小和选项（MSS、窗口缩放、是否支持 SACK）。动画先把序号走清楚，选项不画。

### 四次挥手

TCP 是全双工。A 到 B 的字节流和 B 到 A 的字节流各关各的。

主动关闭的一方发 `FIN`。FIN 也占一个序号。没有传过应用数据时，客户端的 SYN 用了 100，FIN 就是 101。

1. 客户端 → 服务器：`FIN, seq = u`。客户端进入 FIN_WAIT_1。它不再写新数据，但还能读。
2. 服务器 → 客户端：`ACK, ack = u + 1`。服务器进入 CLOSE_WAIT，客户端进入 FIN_WAIT_2。服务器还可以把没写完的响应写完。
3. 服务器 → 客户端：`FIN, seq = v`。服务器进入 LAST_ACK。
4. 客户端 → 服务器：`ACK, ack = v + 1`。客户端进入 TIME_WAIT，服务器收到后关闭。

第 2、3 步有时并进同一个包。那是实现上的合并，语义仍是「确认你的 FIN」加上「我这一侧也关了」。

TIME_WAIT 在主动关闭的一方，大约等 2MSL（报文最多能在网络里活多久，再乘二）。两件事：最后这个 ACK 若丢了，对方会重发 FIN，我还得在，才能再确认一次；同时等旧连接的迟到报文死掉，避免串进下一个用同一对端口的连接。

### 序列号与确认

TCP 给应用的是字节流，不是消息流。写两次 `"ab"` 和 `"cd"`，对方可能一次读到 `"abcd"`，也可能拆开。没有包边界。前端说的粘包、拆包，是流的本性，要在应用层自己分帧：长度前缀、分隔符，或一行一条 JSON。

序号是字节偏移。确认号是累积的：`ack = N` 表示 N 之前的字节都到了，请从 N 接着发。中间缺一个字节，确认号就停在洞上，哪怕后面的字节已经到了。

本目录的 demo 故意改简单了：一条消息占一个序号。看窗口比较清楚。看完要记得真 TCP 按字节编号。

### 滑动窗口与流量控制

停等协议（发一个、等 ACK、再发下一个）是对的，但链路大部分时间是空的。往返一次要一个 RTT，一个小报文填不满带宽。

滑动窗口允许最多 W 个「已发出、未确认」的字节同时在路上。demo 里 W 是报文个数。每收到向前走的 ACK，窗口左沿就往右滑，腾出新名额。

接收方还会通告自己还能收多少。没确认的数据不能超过这个值。对端读得慢，把通告窗口收成 0，发送方就停。这叫流量控制，保护接收方，不保护网络。

窗口收到 0 之后怎么再探开，这里不展开。动画里窗口大小固定，先把「在途有上限，ACK 一到就滑动」看顺。

### 丢包重传

发送方给最早没被确认的数据设超时（RTO）。到点还没有能盖过它的 ACK，就重传。

RTO 不能拍脑袋。太短，ACK 还在路上就重发，一堆重复；太长，丢了也迟迟不补。TCP 用往返时间的均值和波动来估，连续超时还会退避，避免越丢越猛地灌。

只靠超时会慢。后面的包到了、前面有洞时，接收方会反复确认同一个序号。发送方连看几个一样的 ACK，可以不等超时，先把洞补上。这叫快重传。demo 和滑动窗口动画只做了超时重传，重复 ACK 会在日志里出现，但不会提前重发。

### 拥塞控制入门

流量控制不管路由器。大家都按接收窗口往外灌，队列溢了，包被丢掉，重传又灌进去，会塌。

发送方再加一个限制：拥塞窗口 cwnd。真正在路上的量，是接收窗口和 cwnd 里较小的那个。

用 Reno 建立图像就够了，现代内核多用 CUBIC、BBR，形状不同，要回答的问题一样：

- 慢启动：cwnd 从很小开始，大约每个 RTT 翻倍。名字叫慢，其实是指数涨，只是起点低。
- 拥塞避免：过了阈值改成线性加，继续探路。
- 把丢包当成「路大概满了」的信号，把 cwnd 砍下来再探。

无线网络也会丢包，丢了不一定是拥塞，所以后来有算法改去看延迟和交付速率。入门先建立判断：发送方必须自己节流，不能只听接收窗口。

## 动手实验

1. 打开 [三次握手和四次挥手](viz/handshake.html)。用单步走完，说得出每一步谁的状态变了、确认号为什么是那个数。再把丢包率拉高，看重发时序号变不变。
2. 打开 [滑动窗口](viz/sliding-window.html)。丢包率先放在 0，看窗口打满、ACK 回来、左沿右移。再拉到 20% 左右，盯住一个被丢掉的字，等它重传，看先前缓存的字会不会立刻按序出现在底下那句里。把窗口调成 1，对照停等。
3. 跑 demo：`node demo/simulate.js --loss 0.3`。每一行 `丢失` 后面都应有同一个 seq 的 `重传`，最后一句是完整的。再试 `--window 1` 和 `--loss 0`。细节在 [demo 的说明](demo/README.md)。
4. 看一次真的握手。

```bash
sudo tcpdump -i any -n -tttt 'tcp port 80 and host example.com'
curl -s -o /dev/null http://example.com
```

在输出里找前三个带 `S` 标志的包，对一下序号和确认号。没有 tcpdump 权限就用 Wireshark，过滤 `tcp`。HTTPS 外面还有 TLS，先看 TCP 那三下，别和 TLS 握手混在一起。

demo 走的是 UDP 上的教学协议。要抓它自己的包，用 `simulate.js` 打印的中继端口，对着回环接口抓 UDP。那不是 TCP，是用来对照序号、确认和重传。

## 自测题

先盖住答案。

1. 第三次握手的 ACK 丢了，连接会怎样？
2. 为什么挥手常常是四次，握手是三次？
3. 接收窗口和拥塞窗口各在保护谁？
4. 应用写了两次 100 字节，对方一定会按两次 100 字节来读吗？
5. 累积确认号停住不动，能不能说明后面的数据一个都没到？
6. TIME_WAIT 在主动关闭方还是被动关闭方？它主要在等什么？

<details>
<summary>答案</summary>

1. 服务器停在 SYN_RCVD，会重发 SYN + ACK。客户端已经认为连接建立，它发出的数据会促使服务器把握手再确认一遍。多次失败后两边放弃。第三次不是客套。
2. 握手时服务器把「我同意」和「我确认你的序号」放进同一个 SYN + ACK。挥手时对方收到 FIN，往往自己的数据还没发完，只能先 ACK，稍后再 FIN。两个方向各关一次。
3. 接收窗口保护接收方的缓冲，拥塞窗口保护网络。发送方两个都要遵守，取更小的那个。
4. 不一定。TCP 是字节流，没有消息边界。两次写可能被合并，也可能被拆开。
5. 不能。确认号停在洞上。洞后面的数据可能已经在接收方的乱序缓存里，只是还不能交给应用。
6. 主动关闭的一方。等最后的 ACK 还有机会被重传，并等旧报文过期，避免污染下一条同端口的连接。

</details>
