# 12 软件工程

[← 回到路线](../README.md)

设计模式、架构、测试、可观测性、系统设计。这一层是把前面的知识用在一个会变化的程序上。

## 为什么要学

模式和架构图容易学成名词收藏。有用的部分是边界：哪一段会变，哪一段必须稳，失败了怎么被看见。做全栈时，一个接口从「能跑」到「能上线」，差的就是测试、日志和超时这些具体的东西。

## 建议顺序

1. **设计模式** — 少记几个真的会用的：策略（把变化的算法换掉）、观察者（事件）、适配器（把一个接口凑合成另一个）。见到的时候能认，不要按目录背 23 个。
2. **架构** — 先是模块边界和依赖方向，再谈分层。单体里边界清楚，往往比过早拆服务好。拆开的理由是独立部署和故障隔离，不是图更好看。
3. **测试** — 单元测试盯一个函数，集成测试盯几段接在一起。先会读失败信息，再增加数量。测试要能在你改坏协议或边界时变红，像 TCP demo 里的 `selfcheck.js`。
4. **可观测性** — 日志回答「这一次发生了什么」，指标回答「整体健不健康」，追踪回答「这一次请求走过哪些服务」。先把日志里的请求 ID 串起来。
5. **系统设计** — 从一个具体问题开始：谁在用、读写比例、什么可以丢、什么不能丢。容量、缓存、队列、数据库，按这个约束往上加，而不是把所有组件画满。

## 书和课

- 模式：《设计模式》当字典。日常更有用的是《A Philosophy of Software Design》（John Ousterhout）里关于深度和复杂度的几章
- 测试：项目用的那一个框架的文档，加上一本短的《怎么写测试》不如自己把一个小模块补到改坏会失败
- 系统设计：先把 [07](../07-database/README.md) 和 [09](../09-distributed/README.md) 的词用准，再做题。题是练习拆解，不是背架构图

这一节的「demo」可以是给前面某一个协议或数据结构补测试和日志：失败时打印在途的序号，而不是只抛一个 `Error`。
